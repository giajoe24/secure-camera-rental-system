# セキュアカメラ貸出管理システム 設計書

依頼書「15. 出力方法」の順番(1〜15)で整理しています。
コードは別ファイルにあり、起動・導入の手順は README.md にまとめています。

> 表記のルール
> - **PC確認済み** … この開発環境(Linux)で実際に実行して確認したもの
> - **実装済み・実機未確認** … コードはあるが、実機(Raspberry Pi / RC-S380 / 電磁ロック)では動かしていないもの
> - **未確認** … 実行していないもの

## 1. 要件の整理

| 区分 | 内容 |
|---|---|
| 目的 | 社員証で本人確認し、セキュアカメラの貸出・返却を電子記録。記録後に電磁ロックを解錠 |
| 利用者 | 一般利用者(タッチ操作)/ 管理者(コマンドライン) |
| 本番環境 | Raspberry Pi 4 / Debian 13 / Python 3.13.5 / RC-S380 / LE-53 / タッチモニター |
| 開発環境 | Windows PC / Python 3.14 系の可能性 / PowerShell |
| 必須の順序 | **SQLite 記録 → 成功時のみ解錠**。記録失敗時は解錠しない |
| 二重貸出 | 同じカメラを同時に複数人へ貸さない。未返却の人には貸さない |
| モード | デモ(固定カード・GPIO出力なし・DB保存は実施)/ 実機 |
| 分離 | GUI・DB・NFC・GPIO・デモ処理を分ける |
| 品質 | 学習者が読めるコード、日本語コメント、接続の確実な close(WinError 32 の再発防止) |

## 2. 不明点と仮定

開発を止めず、次の仮定で実装しました。違う場合は教えてください。

| # | 不明点 | 仮定(実装した内容) | 違った場合の影響 |
|---|---|---|---|
| A1 | 電磁ロックは何個か | **保管庫1つに電磁ロック1個**。どのカメラでも同じ扉を開ける | カメラごとの扉なら、カメラ→GPIO の対応表を追加(`GpioLockController` を複数持つ) |
| A2 | 1人が同時に借りられる台数 | **1人1台まで**(未返却があれば貸出不可) | 複数台可なら利用者用の部分UNIQUEインデックスを外す |
| A3 | 代理返却 | **借りた本人の社員証でのみ返却**。それ以外は管理者が `force-return` | 代理返却を許すなら返却画面でカメラ選択を追加 |
| A4 | 延滞時の扱い | 延滞でも返却可能。画面と CSV に「延滞」を表示するだけ | ペナルティが必要なら別途設計 |
| A5 | 社員証の種類 | FeliCa / Type A / Type B のいずれか。**カードの固有番号(IDm / UID)で照合** | カード内データで照合する場合は `card_reader.py` を変更 |
| A6 | 時刻 | Raspberry Pi のローカル時刻(日本時間)をそのまま保存 | 複数拠点・タイムゾーン混在なら UTC 保存に変更 |
| A7 | 貸出時間の単位 | 整数の「時間」 | 30分単位などが必要なら分単位に変更 |
| A8 | 画面に利用者名を表示してよいか | ホームの一覧には **表示しない**(状態と返却予定のみ)。履歴画面では表示する | 不可なら `screens_info.py` で氏名を伏せる |
| A9 | CSV 出力を一般画面から行ってよいか | 読み取りのみなので **可**。`ALLOW_CSV_EXPORT_FROM_SCREEN = False` で非表示にできる | — |
| A10 | 依頼書3章で写真の端が切れていた項目 | 後半の再掲から「**貸出・返却履歴の表示**」と判断し実装 | — |
| A11 | DENSO ロゴ | 提供されていないため **生成せず、テキストでシステム名を表示**。正式画像があれば `LOGO_IMAGE_PATH` で表示可能 | — |

## 3. 改善提案

依頼書の案から変更・追加した点です。

| # | 変更・追加 | 理由 | メリット | デメリット |
|---|---|---|---|---|
| P1 | **解錠ログ表(unlock_logs)を追加** | 「DB記録後に解錠失敗」を管理者が後から追えるようにするため | 問い合わせ時に受付番号から経緯が分かる | テーブルが1つ増える |
| P2 | **解錠失敗時の扱いを設計**(貸出: 再試行 / 取消、返却: 再試行 / 自動で点検中) | 「記録済みだが扉が開かない」状態を放置しないため | 利用者が次の行動を選べる。返却時は保管庫にないカメラを次の人に貸さない | 画面が1つ増える |
| P3 | **記録前にロックが使えるか確認** | GPIO 初期化失敗中に貸出記録だけが増えるのを防ぐ | 「記録したのに取り出せない」状態をほぼ発生させない | — |
| P4 | 「未返却 / 返却済み」は列を持たず **returned_at の有無で判定** | 同じ意味の列を2つ持つと食い違いが起きる | データの矛盾が起きない | SQL で `returned_at IS NULL` と書く必要がある |
| P5 | **部分UNIQUEインデックス**で二重貸出を DB レベルでも禁止 | プログラムの確認だけでは、将来の改修ミスで破られる可能性がある | DB が最終防衛線になる | SQLite 3.8 以降が必要(Pi・Windows とも満たす) |
| P6 | 解錠失敗の取消は **削除せず「取消(解錠失敗)」として終了** | 監査上、記録を消さない | 経緯が残る | 履歴に取消行が残る |
| P7 | デモ用DBを **別ファイル** に分離 | デモデータと本番データの混在を防ぐ | 実機で安心してデモを試せる | ファイルが2つになる |
| P8 | **無操作タイムアウト**(60秒でホームへ) | 認証後の画面を放置されると、次の人が他人の名前で操作できてしまう | なりすまし操作を防ぐ | 操作が遅い人は時間切れになる可能性(設定で変更可) |
| P9 | 一覧を **スクロールではなくページ送り** | タッチモニターでは指でなぞってもスクロールしにくい | 確実に操作できる | 件数が多いとページ数が増える |
| P10 | 借りられるカメラがない場合は **社員証をかざす前に案内** | かざした後で断られるのは不親切 | 無駄な操作が減る | 認証後にも再確認する(同時操作対策) |
| P11 | 起動オプション `--demo` / `--real` / `--demo-unlock-fail` | 設定ファイルを書き換えずに切り替えたい | 確認が楽 | 設定とオプションの優先順位を覚える必要(オプション優先) |
| P12 | 「貸出中」は **青** で表示 | 貸出中は異常ではないので赤・黄を使わない | 警告色の意味が明確になる | 依頼書の色指定にない色を1つ追加 |
| P13 | CSV は **UTF-8 BOM付き + 数式インジェクション対策** | Excel で文字化けしない / 氏名が `=` で始まっても数式にならない | 安全に開ける | — |
| P14 | 管理ツールに `disable-user` / `set-camera-status` / `force-return` / `unlock-logs` / `check` を追加 | 運用中に必ず必要になる操作 | 管理者が DB を直接触らずに済む | コマンドが増える |
| P15 | 管理ツールは操作対象の DB を **毎回表示** | デモ用/実機用の取り違え防止 | 誤登録を防ぐ | 出力が1行増える |

採用しなかった案:

- **管理画面(GUI)の追加**: タッチ画面から管理機能に入れると、PIN の管理などで逆に安全性が下がるため、今回はコマンドラインのみとしました。必要であれば「管理者用カードでのみ開く管理画面」を次の段階で提案します。
- **カメラ状態の列を廃止して貸出記録から算出**: データの正しさの点では優れていますが、依頼書の「状態」の定義と学習しやすさを優先し、状態列を残して同一トランザクションで更新する方式にしました(食い違いは `manage_data.py check` で検出できます)。

## 4. システム構成

```
┌──────────────────────── 画面(gui/) ────────────────────────┐
│ app.py(ウィンドウ・画面切替・タイムアウト・エラー表示)            │
│ screens_flow.py(ホーム・貸出・返却の流れ) screens_info.py(履歴)   │
└───────────────┬───────────────────────────┬──────────────────┘
                │ 呼び出し                    │ 別スレッドで read_card()
                ▼                            ▼
┌──── rental_service.py ────┐     ┌──── hardware/card_reader.py ────┐
│ 貸出・返却の手続き           │     │ NfcCardReader(RC-S380/nfcpy)  │
│ ①確認 ②DB記録 ③解錠 ④ログ  │     │ DemoCardReader(デモボタン)     │
└──────┬─────────────┬──────┘     └──────────────────────────────┘
       │             │
       ▼             ▼
┌ database.py ┐  ┌──── hardware/lock_controller.py ────┐
│ SQLite      │  │ GpioLockController(gpiozero)        │
│ 接続ごとclose│  │ DemoLockController(出力なし)         │
└─────────────┘  └──────────────────────────────────────┘

manage_data.py(管理者) ──▶ database.py / rental_service.py
tools/check_*.py(単体確認) ──▶ hardware/*
```

ポイント:

- 画面は「デモか実機か」を知りません。`hardware/__init__.py` が設定を見て部品を作り、画面に渡します。
- 「DB記録 → 解錠」の順番は **rental_service.py の中だけ** で守ります。画面側が順番を間違える余地をなくしています。
- カード読み取りは待ち時間があるので別スレッドで行い、結果は `queue` 経由で画面スレッドに渡します(画面部品は画面スレッドからしか触りません)。

## 5. 画面遷移

※ 2026/11/11 に画面デザインを作り直しました(「駅の券売機のように迷わない画面」が方針)。
配置の理由は、この章の最後の「画面の配置の理由」にまとめています。

```
ホーム(左: カメラごとの状態 / 右: 借りる・返す / 左下: 履歴)
 │
 ├─ カメラを借りる(貸出可能0台ならここで案内)
 │    ① 社員証 ──▶ ② カメラ ──▶ ③ 貸出時間 ──▶ ④ 確認 ──[貸し出す]──▶ ⑤ 完了
 │      │           押すと次へ     押すと次へ                  │
 │      │                                                    ▼
 │      │                                           SQLite に記録 → 解錠
 │      └ 未登録・利用停止・読取失敗・時間切れ・未返却あり → お知らせ画面
 │
 └─ カメラを返す
      ① 社員証 ──▶ ② 確認 ──[返却する]──▶ ③ 完了
        └ 返却対象なし など → お知らせ画面

SQLite への記録に失敗 → エラー画面(扉は開けていません)
解錠に失敗           → 「扉が開きませんでした」(受付番号)
                         貸出: [貸出を取り消す] ← → [もう一度開ける]
                         返却: [管理者に連絡する] ← → [もう一度開ける](カメラは自動で点検中)
完了                 → 「扉が開きました。カメラを取り出して、扉を閉めてください。」
                         施錠に戻る秒数を表示し、時間が来たらホームへ
```

- 社員証読み取り・解錠中の画面以外は、**60秒操作がなければホームへ戻ります**。
- 解錠失敗画面(貸出)で放置された場合は、貸出を自動で取り消してからホームへ戻ります
  (本人が取り出せていないのに「未返却」扱いになるのを防ぐため)。


### 画面の配置の理由

| 画面・部品 | 配置 | 理由 |
|---|---|---|
| 全画面共通 | 上: 手順 / 中: 見出し1行 + 説明1行 + 中身 / 下: ボタン帯 | どの画面でも「上で現在地、中で内容、下で操作」と同じ順に読めるようにした |
| 手順表示 | 画面上部に「① 社員証 → ② カメラ → …」、今の手順だけ赤字+下線 | あと何回押せば終わるかが分かると、途中で迷ったりやめたりしにくい |
| 下部ボタン | 「戻る/やめる」は必ず左下、「貸し出す/返却する」は必ず右下。大きさも固定 | 位置が画面ごとに変わると毎回探すことになる。前へ進む操作を右にそろえると指の動きが一定になる |
| ボタンの文言 | 「OK」「次へ」ではなく「貸し出す」「返却する」「もう一度かざす」 | 押したら何が起きるかがボタンだけで分かる |
| ホーム | 左: カメラの一覧(名前・状態・返却予定)、右: 「借りる」「返す」の大きなボタン2つ | 借りられるカメラがあるかを、ボタンを押す前に一目で確認できる。操作は2択だけにした |
| ホームの左下 | 「履歴を見る」 | ホームには戻る先がないので、左下の位置を補助機能に使った(主な操作と混ざらない) |
| カメラ選択・時間選択 | 1画面1つ。選択肢を縦に並べ、押すとすぐ次へ | 「選ぶ」と「次へ」の2回押しをなくす(券売機と同じ)。返却予定はボタンの中に書き、押す前に分かるようにした |
| 確認画面 | 項目名と値を左右に並べた表 | 確認するのは値だけなので、値を太字で左端をそろえた |
| 完了画面 | 「扉が開きました。カメラを取り出して、扉を閉めてください。」を一番大きく | 手続きは終わっているので、利用者が次にする体の動きだけを伝える |
| エラー画面 | 左上に「エラー/注意」の札、見出しに何が起きたか、1行で次にすること | 色だけに頼らず文字で種類が分かる。長い説明は読まれないので1行にした |
| 色 | 赤=押せる主な操作、緑/青/黄=状態だけ。影・グラデーション・アイコンは使わない | 色に意味を持たせると、装飾がなくても見分けられる |
| 左寄せ | 見出し・説明・表はすべて左寄せ | 中央寄せは行頭がそろわず読みにくい。視線を左上から右下へ流す |
| 無操作 | 60秒でホームへ(読み取り中・扉が開いている間を除く) | 認証後の画面を放置されると、次の人が他人の名前で操作できてしまう |

### インデックス

| 名前 | 内容 | 目的 |
|---|---|---|
| ux_rentals_open_camera | `UNIQUE (camera_id) WHERE returned_at IS NULL` | **1台のカメラの未返却貸出は1件まで**(二重貸出防止の最終防衛線) |
| ux_rentals_open_user | `UNIQUE (user_id) WHERE returned_at IS NULL` | **1人の未返却貸出は1件まで**(再貸出防止の最終防衛線) |
| ix_rentals_rented_at | `(rented_at)` | 履歴を新しい順に表示 |
| ix_unlock_logs_created_at | `(created_at)` | ログの表示 |

### 日時の保存形式

`2026-11-10 20:15:00` の文字列(ローカル時刻)。文字列のまま大小比較でき、DB を直接見ても読めます。

### トランザクション設計

- **1操作 = 1接続 = 1トランザクション**。接続は `_open_connection()` の `finally` で必ず `close()` します。
  - `with sqlite3.connect(...)` は commit/rollback はしますが **close しません**。これが以前の WinError 32 の原因と考えられます。
- 書き込みは `BEGIN IMMEDIATE` で開始(確認の SELECT と更新の間に他の書き込みを入れない)。
- ブロックが成功すれば `commit()`、例外なら `rollback()`。
- 外部キー制約は接続ごとに `PRAGMA foreign_keys = ON`。
- 貸出(`create_rental`)は次を1トランザクションで実行:
  1. 利用者が利用可能か
  2. 未返却の貸出がないか
  3. `UPDATE cameras SET status='rented' WHERE id=? AND status='available'`(更新0件なら貸出不可)
  4. `INSERT INTO rentals`
- 返却(`finish_rental`)は「返却日時の記録」と「カメラ状態を戻す」を1トランザクションで実行。
- 解錠ログの保存失敗では、貸出・返却を取り消しません(ログより本体の記録を優先)。
- ジャーナルモードは SQLite 標準(DELETE)。WAL は `-wal` / `-shm` ファイルが増え、
  学習者には分かりにくいため採用していません(1台・1プロセスの利用では性能差は問題になりません)。
- `PRAGMA user_version` でスキーマの版を管理(将来の列追加に備える)。

分け方の考え方:

- **層ごとに分ける**(gui / service / database / hardware)。依頼書の「GUI、DB、ハードウェア処理を分離」を満たし、ファイル名から役割が分かるようにしました。

## 8. 実装方針

| 項目 | 方針 | 理由 |
|---|---|---|
| 設定管理 | `config.py`(Python の定数) | コメントが書け、追加ライブラリ不要。起動オプションで一部上書き |
| ログ | 標準 `logging`。コンソール + `logs/camera_rental.log`(1MB×5世代) | SD カードを埋めない |
| エラー表示 | 独自例外 `CameraRentalError` に「見出し」「利用者向け説明」を持たせる。想定外の例外は一般的な案内のみ表示し、詳細はログへ | Python の例外文を画面に出さない |
| 最終防衛線 | `report_callback_exception` を上書きし、画面処理中の想定外例外もエラー画面にする | 画面が固まったように見えるのを防ぐ |
| スレッド | 読み取りのみ別スレッド。結果は `queue` → `after()` で画面スレッドが受け取る。画面を離れたら `Event` で読み取りを中止 | CustomTkinter はスレッドセーフではない |
| 時間差処理 | `after()` の予約は画面ごとに管理し、画面を離れるときに全部取り消す | 破棄済みの部品を更新するエラーを防ぐ |
| 二度押し防止 | 「確定」ボタンは押した瞬間に無効化 | 2回記録されるのを防ぐ(DB制約でも防止) |
| 画面の作り直し | 画面は使い回さず毎回作る | 前の利用者の情報が残らない |
| 解錠 | `unlock()` は ON にしてすぐ戻り、`threading.Timer` で OFF に戻す。終了時は必ず OFF → GPIO 解放 | 画面を止めない・終了時に開きっぱなしにしない |
| 共通UI部品 | `widgets.py` に関数とクラスで最小限(ボタン、バッジ、表、ページ送り、画面の親クラス) | 色や大きさの重複をなくす |
| テスト | 標準 `unittest` + 入口の `self_test.py` | 下記参照 |

**テストに unittest を選んだ理由**: 標準ライブラリなので Windows・Pi の両方で追加インストールなしに動き、
`discover` でテストを自動収集できます。pytest でもそのまま実行できます。
独自 self_test だけだとテストが増えたときに管理しにくいため、「中身は unittest、入口は self_test.py」としました。

## 9. リスク

| リスク | 内容 | 対策・推奨 |
|---|---|---|
| カードの複製 | IDm / UID は暗号的な認証ではなく、複製カードやエミュレーターで偽装されうる | 社員証発行元の仕様で、認証付きの読み取り方式を検討。高いセキュリティが必要なら PIN 併用 |
| ランダム UID | 一部のカード・スマートフォンは読むたびに UID が変わる | `check_card_reader.py` で同じカードを複数回読んで確認 |
| 物理的な持ち出し | 保管庫が1つの場合、扉が開いている間は選んだ以外のカメラも取り出せる | 運用ルール、または将来カメラごとの扉・在庫センサー |
| 返却は自己申告 | 返却は「記録 → 解錠」の順なので、扉を開けた後に実際にカメラを戻したかはシステムでは分からない | 施錠センサーで扉が閉まったことは確認できるが、カメラの有無は分からない。定期的な棚卸し、または将来の在庫センサー |
| 時刻のずれ | Pi 4 には RTC がなく、NTP なしで起動すると時刻がずれる | NTP 同期の確認、または RTC モジュール追加 |
| 解錠後に扉を閉め忘れ | 施錠に戻っても扉が開いたままなら意味がない | **対応済み(設定で有効化)**: LE-53 のカムスイッチを GPIO 入力で読み、完了画面で「閉めてください」と案内、待ち時間切れで「管理者に連絡」、ホーム画面でも警告 |
| 電磁ロックの発熱 | LE-53 は連続通電で約 70℃(製品ページ)。連続通電時間の定格は未確認 | `UNLOCK_SECONDS` を仕様書の定格内に。やけど対策 |
| 停電 | LE-53 は非通電で施錠のため、停電時は開かない。非常解錠機構の記載なし | 棚の物理キーなどの非常手段 |
| カードリーダーの調達 | RC-S380 / RC-S380/S は生産終了。後継 RC-S300 は nfcpy の対応一覧にない | 予備機の確保。将来は RC-S300/S1 + PC/SC(pyscard)の読み取りクラスを追加 |
| 公式サポート外の構成 | RC-S380 の公式対応 OS は Windows のみ。Pi では nfcpy(コミュニティ)で使う | 実機での読み取り確認を必須とする |
| SD カード破損 | 電源断で DB が壊れる可能性 | 定期バックアップ(`data/` のコピー、または CSV 出力)。安全なシャットダウン |
| 同時操作 | 管理ツールとアプリの同時書き込み | `BEGIN IMMEDIATE` + `timeout=5` で待機。失敗時は保存失敗として扱う |
| ライブラリの保守 | nfcpy は 2021 年以降更新がない | 今回の環境で import できることは確認済み。将来は代替ライブラリも検討 |
